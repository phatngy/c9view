## R1. Minimum Claude Code version (FR-017)

- **Decision**: the minimum is **2.1.318**, the only version the spike verified end to end. It is a constant in `packages/node/src/remote/version.ts` (`REMOTE_MIN_VERSION`), not an environment setting, and is recorded in `docs/data-sources.md` with the date and platform of the spike that verified it. A session whose `version` is missing, unparsable or lower is unavailable with reason `too-old` and "Update Claude Code to 2.1.318 or newer". Comparison is numeric on `major.minor.patch`; any pre-release or build suffix counts as unparsable (fails closed).
- **Raising or keeping it**: on every Claude Code upgrade the maintainer reruns the re-spike ([R13](#r13-re-spike-items), about two Haiku turns). If the new version passes, the minimum stays and `docs/data-sources.md` gains a "verified also on X" line. If the wire format or transcript records changed, the minimum is raised to the first passing version in the same PR that adapts the code. Lowering it needs a spike run on the older build.
- **Rationale**: the clarified spec (Q4) says the minimum is the spike-verified version. The frame (`msgV:1`, `msg_id`, the `<cross-session-message>` wrapper) and the transcript's `origin` fields are undocumented; nothing shows they exist in 2.1.224. An older session would accept or silently ignore a frame (unknown `type` values are ignored without error, spike risk 3), which looks like a hang.
- **Alternatives**: the documented 2.1.224 as an unverified floor (rejected: fails open on the undocumented parts); a `C9VIEW_REMOTE_MIN_VERSION` override (rejected: lets a setting lower a safety gate; a code change with a spike run is the right path).

## R2. Address source: live status file, no hook

- **Decision**: the node reads the address only from Claude Code's live status file `<claudeDir>/sessions/<pid>.json` (`messagingSocketPath`), at every availability check and again right before every send. **No hook change and no new state-folder record.** c9view never stores the address: it is held in memory only for the duration of one check or send, then dropped. The `*.key` files beside the JSON are never listed by name pattern, opened or logged (002's `readLiveEntries` and `liveness.ts` already filter to `*.json`). c9view never opens `*.key` files and never keeps, parses into a field, logs, stores or returns a `peerToken` that appears in a status file. Discovery parses the status file with an explicit pick schema (`.strip()`, never passthrough), so the token is dropped at parse time. The frame carries no auth line.
- **Rationale**: the spike shows the JSON carries everything needed and more than a hook would give: `messagingSocketPath`, `version` (FR-017), `peerProtocol` (R7), `pid` and `procStart` (FR-003 ownership), `status` (idle, busy, waiting) and `sessionId`. Claude Code removes the file and socket on a clean exit, so there is no c9view record to expire. A hook would add a new kind of state-folder data (a constitution change), a second writer, and an install step the owner must rerun, and it still could not cover sessions started before the hook was installed. The JSON is already a constitution-listed input (Principle IV) that c9view parses today. Fewer writes is better (Principle I).
- **Hook as fallback**: rejected. Every session that runs a version at or above the minimum writes `messagingSocketPath` (spike Q1); a session without it is either too old or has messaging off, and a hook would not change that. A hook-recorded path would also need the same ownership checks, so it adds no reach.
- **Spec impact** (dated amendments proposed in [amendments.md](amendments.md#003-spec)): FR-004 ("stored only in c9view's state folder", "c9view's installed hook records only the address") and FR-005 (the hook) become moot; the Clarifications Q2 answer is kept as history with a note; the edge case "Session started before c9view could learn its address" and User Story 4 scenario 2 ("how to make it reachable") change to "the session's live status file names no messaging address (update Claude Code, or turn on cross-session messaging in that session)"; the Constitution-impact assumption drops the "new kind of data" half; Key Entity "Session messaging address" says "read from Claude Code's live status file, never stored".

## R3. Constitution amendment

- **Decision**: one MINOR amendment (1.0.0 → 1.1.0) to Principle I, through `/speckit-constitution` in its own PR (**003-0**), merged before the first PR that sends anything (003-b). With no hook there is no new state-folder data, so only the "processes c9view did not start" part remains. Proposed text and the matching `AGENTS.md` and `docs/data-sources.md` edits are in [amendments.md](amendments.md#constitution).
- **Rationale**: Principle I says c9view writes nothing under `~/.claude` and that only "the Claude Code processes it starts with control on write their own data". Delivering a message makes a process c9view did not start write to its transcript as a direct result of a c9view action. That is materially new behaviour of an existing principle (MINOR per Governance), even though c9view's own code writes no file. Recording it keeps the "every exception is listed" property of Principle I. Principles II, III, V apply unchanged (II gains no new rule: addresses and message text are already covered by "logs MUST NOT contain secrets or message content"; the plan adds tests).
- **Alternatives**: no amendment, arguing that a socket write is not a file write (rejected: the principle is about what changes the owner's Claude data, and the receiving session's transcript changes because c9view asked it to); a PATCH (rejected: it adds a new permitted action).

## R4. Wire frame and attribution (FR-011)

- **Decision**: `packages/node/src/remote/frame.ts` builds exactly one line:

  ```json
  {"msgV":1,"msg_id":"<uuid v4>","type":"user","message":{"role":"user","content":"<wrapper>"},"priority":"next","from":"uds:/dev/null/c9view"}
  ```

  followed by `\n`. No auth line. `content` is:

  ```text
  <cross-session-message from="uds:/dev/null/c9view" from-name="c9view">
  Sent by this session's owner from c9view.

  <owner's text>
  </cross-session-message>
  ```

  - `from` marker `uds:/dev/null/c9view`: constant, leaks nothing, and can never be a socket: `/dev/null` is a character device, so any path under it fails with `ENOTDIR` for every user. The receiver connects to `from` only to report hold or refuse, and that connection fails harmlessly instead of reaching another listener (a real or guessable path could reach another Claude session and inject a delivery notice there).
  - `from-name="c9view"`; **no `from-mode`** (an unauthenticated claim that could change how a bypass-mode receiver treats the message, spike risk 4).
  - Attribution line (FR-011): `Sent by this session's owner from c9view.` It states the source and carries no instruction meant to raise authority; the receiver still wraps it as a message from another session.
  - The owner's text is refused with 400 `bad-text` if it contains `cross-session-message` (case-insensitive), so it cannot close the wrapper and forge attributes. Text starting with `/` is allowed and sent as plain text; the web warns first.
- **Rationale**: matches Claude's own 2.1.318 frame (spike Q2) so `origin.msg_id`, `origin.from`, `origin.name` and `origin.body` are kept, which the delivery tracker (R5) and the label (R6) need. `priority:"next"` is what Claude sends.
- **Alternatives**: the minimal frame without `msgV` (rejected: `origin.from` becomes `unknown`, no `msg_id`, no label); a `from` under c9view's state folder (rejected: leaks the home path into the transcript and, if anything ever listened there, the receiver would talk to it); sending no wrapper (rejected: no `from-name`, so the terminal shows "unidentified session").
- **Re-spike (item 4, answered yes)**: delivery works with this exact `from`; `origin.from` and `origin.name` are kept as given; hold and refuse notices fail quietly (nothing visible to the sender). See [Re-spike (2026-11-05)](spike.md#re-spike-2026-11-05).

## R5. Delivery confirmation and outcomes (FR-007–FR-009, US2, SC-002)

- **Decision**: the socket never answers (spike Q2, Q5), so the outcome comes in steps, kept in the receipt's new `delivery` field ([data-model.md](data-model.md#remotedelivery)):
  1. **`sent`**: the frame was written and the connection ended without error. The receipt settles here (`status: 'done'`) and the route returns 202. This is the outcome SC-002's 2 seconds applies to.
  2. **`delivered`**: the tracker found a transcript record with `origin.kind === "peer"` and `origin.msg_id` equal to the generated `msg_id`: a `type:"user"` record → `turn: 'new-turn'` ("Delivered: Claude is starting a new turn"); an `attachment` record with `attachment.type === "queued_command"` → `turn: 'next-step'` ("Delivered: Claude sees it at its next step"). The turn comes from the record type, never from the `status` read at send time, so a state change between check and delivery is reported as it happened (edge case "Idle versus mid-turn"). `deliveredAt` is the transcript record's own timestamp, not the time the tracker saw it. A message released from a hold keeps its original `msg_id` (item 5), so it matches the same way; its record timestamp is the release time. There is no earlier "accepted by the session" step: `queue-operation enqueue` carries no `msg_id` (item 2, answered no), so the tracker matches only `user` and `attachment.queued_command` records.
  3. **`not-seen`**: no record after `C9VIEW_REMOTE_NOT_SEEN_SEC` (default 20 s; mid-turn delivery can lag by a long tool call, so a `not-seen` receipt may still become `delivered`). Shown as "Sent, not seen yet: the session may be busy with a long step, or holding or refusing messages". Tracking continues; a held message the owner later lets in at the terminal turns the receipt into `delivered` while the receipt lives.
  4. **`uncertain`**: the write timed out (`C9VIEW_REMOTE_SEND_TIMEOUT_SEC`, default 3 s) or the connection broke after part of the frame was written. Part of a frame followed by a close can still be delivered (spike Q6), so it is "This may have been sent", never resent, and still tracked; it can become `delivered`.
  5. **`failed`** with `reason`: `session-ended` (connect `ENOENT` or `ECONNREFUSED`, or `EPIPE`/`ECONNRESET` before any byte, when the PID is dead or its `procStart` no longer matches; a killed session leaves its socket and JSON behind and the connect gives `ECONNREFUSED`, item 6), `unreachable` (the same errors while the process is alive and matches, and `ENOTSOCK`, `EACCES`). Nothing was delivered; the text stays in the composer.
- **Held vs refused**: indistinguishable from outside (spike Q5). c9view does not claim either after sending. Before sending it works out what the session will probably do with the message (`packages/node/src/remote/inbound.ts`, read-only, see [R7](#r7-gating-ownership-checks-and-error-mapping-fr-002-fr-003-fr-018) step 15 for the rule). Result: `refuse` → unavailable `inbound-refused` with the fix; `hold` (set, or an invalid value) → available with the hold warning "This session holds messages until you let them in at the terminal"; unset and the receiver is in `bypassPermissions` or its mode is unknown → available with the softer "may hold" warning; otherwise no warning. Managed policy and `--settings` flag sources cannot be read by c9view, so the result is advisory and "not seen yet" stays the fallback. The setting can also change inside the session (`/config` writes the user settings file, which c9view reads), so a fresh check runs before each send. A held message the owner releases later keeps its `msg_id` and turns the receipt into `delivered` while the receipt lives; if the receipt has expired the conversation still shows the label (R6). A held message also expires if nobody approves it (the sender cannot see this).
- **Queue full**: undetectable (the receiver drops silently); it shows as `not-seen`.
- **Tracking**: in memory only, in `packages/node/src/remote/tracker.ts`: `msg_id → { operation key, projectId, sessionId, transcript file, byte offset at send }`. It reads from the stored offset to the end on every `session` event for that session (002's watcher already emits it) and every 2 s as a fallback, keeps the offset at the last complete line, and stops at `delivered` or when the receipt expires (`C9VIEW_CONTROL_RECEIPT_MIN`, 10 min). It never rereads from the start (Principle VI). After a node restart the tracker is gone; the conversation still shows the message with its label (R6).
- **Web notification**: on each transition the node emits `control.remote { clientRequestId, projectId, sessionId }` (IDs only, 002 FR-018); the web refetches the receipt.
- **Spec impact**: FR-008's four outcomes (delivered, held, refused, failed), User Story 2 scenarios 1–4 and SC-002 assume the session reports outcomes. Dated amendments in [amendments.md](amendments.md#003-spec).
- **Alternatives**: posing as a registered Claude session to receive `peer_message_status` frames (rejected: would need a socket under `cc-socks` and a fake `sessions/*.json`, i.e. writing Claude data); using `status` at send time for new turn vs next step (rejected: a guess).
- **Re-spike (answered)**: the mid-turn `attachment.queued_command` origin carries `msg_id`, `from` and `name` (item 1, yes); `queue-operation enqueue` carries no `msg_id` (item 2, no, so no earlier step); a released held message keeps its `msg_id` (item 5, yes). See [Re-spike (2026-11-05)](spike.md#re-spike-2026-11-05).

## R6. "Sent from c9view" label (FR-013, US3)

- **Decision**: core recognises peer records in `packages/core/src/transcript/peer.ts` with tolerant Zod schemas (`origin` with `kind`, `from`, `name`, `msg_id`, `verifiedPeerPid`, `verifiedPeerProcStart`, `body`, all optional, passthrough):
  - A `user` record, or an `attachment` record with `attachment.type === "queued_command"`, whose `origin.kind === "peer"` is a peer message.
  - It is **from c9view** when `origin.from === "uds:/dev/null/c9view"` and `origin.name === "c9view"`. Both record types carry these fields (re-spike item 1), so there is no wrapper-content fallback. Parsing stays tolerant: a record that lacks either field is a peer message with no c9view label (`sentFrom: 'peer'`), never an error.
  - Its display text is `origin.body` with the exact attribution line removed (if `body` is missing, the record's own content is shown as for any other peer). Other peers' messages keep today's display (meta record) and get no label.
  - `Message` gains `sentFrom?: 'c9view' | 'peer'` and `sentFromVerified?: boolean` (additive, `packages/api/src/index.ts`). Verified means `origin.verifiedPeerPid` and `verifiedPeerProcStart` equal the current node process (read once from `/proc/self/stat`); `from` and `name` are unauthenticated, while the verified PID comes from the kernel (`SO_PEERCRED`).
  - The web shows the "Sent from c9view" label on both; an unverified one gets the accessible description "Marked as sent from c9view; c9view can't confirm this after a restart". Terminal-typed messages (`origin.kind === "human"` or no origin) never get it.
- **Rationale**: transcript-driven, so the label survives receipt expiry and restarts (FR-013 first branch; the spike shows the transcript keeps the markers). The constant `from` keeps other peers unlabelled. The verified flag keeps the label honest (Principle VII) because any same-user process could forge the marker.
- **Alternatives**: label only while the receipt lives (rejected: the spike shows the transcript is enough); persisting sent `msg_id`s (rejected: new state data).

## R7. Gating, ownership checks and error mapping (FR-002, FR-003, FR-018)

- **Decision**: one function, `check(projectId, sessionId)` in `packages/node/src/remote/availability.ts`, decides availability; the GET route calls it, and the send calls it again right before connecting. It fails closed at the first failed step:

  | # | Check | Reason when it fails |
  | - | ----- | -------------------- |
  | 1 | Control on (route 404 otherwise); receipts not at the tombstone cap | (404) / `control-unavailable` |
  | 2 | Platform is Linux (WSL included) | `unsupported-platform` |
  | 3 | Session exists in the project | (404) |
  | 4 | Not one of c9view's own runs (`runs.bySession`) | `own-run` (use 002's reply) |
  | 5 | Exactly one `sessions/*.json` entry for the session parses; one unparsable file that names the session → unknown | `liveness-unknown` |
  | 6 | No entry, or the PID is not alive | `not-live` (use 002's reply) |
  | 7 | `pidDomain` matches the node's PID namespace; `pid` present | `liveness-unknown` |
  | 8 | `procStart` (a decimal string) equals field 22 of `/proc/<pid>/stat`, parsed after the last `)` of the line so a `comm` with spaces or parentheses cannot shift the fields | `address-invalid` |
  | 9 | `kind === "interactive"` **and** `entrypoint === "cli"` (`claude -p` runs are `interactive` with `entrypoint: "sdk-cli"`; `bg`, `daemon` and `daemon-worker` kinds also exist) | `not-interactive` ("not an interactive terminal session") |
  | 10 | `version` ≥ 2.1.318 (R1) | `too-old` (with `minVersion`) |
  | 11 | `peerProtocol === 1` | `unknown-protocol` |
  | 12 | `messagingSocketPath` present | `no-address` |
  | 13 | Path is absolute, normalised, basename `<pid>.sock`, directly inside an allowed folder: `$XDG_RUNTIME_DIR/cc-socks`, `/run/user/<uid>/cc-socks`, `<os.tmpdir()>/cc-socks-<uid>` or `/tmp/cc-socks-<uid>` | `address-invalid` |
  | 14 | `lstat` of the folder: a real directory owned by the node's uid, not group- or world-writable; `lstat` of the path: a socket, owned by the node's uid, mode `0600` (no group or other bits) | `address-invalid` |
  | 15 | The inbound rule (below) does not give `refuse` | `inbound-refused` |

  Step 6 also covers a stale `sessions/<pid>.json`: after a crash or `SIGKILL` the JSON and socket stay, and the JSON's `status` goes stale. A dead PID means `not-live`, and `status` is read only after steps 6–8 pass.

  **Step 15, the inbound rule** (re-spike item 7; `packages/node/src/remote/inbound.ts`; not the generic `mergeSettings`, whose precedence is wrong for this key). Values are `accept`, `hold`, `refuse`.
  1. Managed policy, then the `--settings` flag file, then user settings: the first that defines the key wins. c9view cannot read the first two, so the user value is the base and the result is advisory. `inbound.ts` is a small dedicated reader, not `readSettings`, `mergeSettings` or `settingSource`. It reads exactly three layers through core's root-confined `readTextResult` (`packages/core/src/claude-config/shared.ts`): user = `<claudeDir>/settings.json` only (`<claudeDir>/settings.local.json` is ignored for this key); project = `<cwd>/.claude/settings.json`; local = `<cwd>/.claude/settings.local.json`, where `cwd` is the status file's `cwd`. It parses only `crossSessionInbound` with Zod.
  2. Project and local layers can only tighten, with order accept < hold < refuse. A value stricter than the current result replaces it; a looser one is ignored. A repo `accept` therefore never beats a user `hold`, and with nothing in the user file a repo `accept` changes nothing.
  3. An invalid value, or a layer that exists but can't be read or parsed, counts as `hold` (Claude Code holds everything while one is present). A missing file is simply unset.
  4. If the result is still unset, the default depends on the receiver's permission mode. A prompting-class mode (`default`, `acceptEdits`, `plan`, `auto`) accepts a sender that asserts no mode, and c9view never sends `from-mode`, so: no warning. `bypassPermissions` holds such a sender, and an unknown or missing mode is held too: warning "may hold".
  5. The receiver's mode comes from the session transcript, not the status file (`sessions/<pid>.json` has no permission-mode field). `packages/node/src/remote/mode.ts` reads a bounded tail of the transcript (the last 64 KiB), Zod-tolerant, using core's `permissionModeRecordSchema` (`packages/core/src/transcript/schemas.ts`) and the same record logic as `permissionModes` in `packages/core/src/transcript/summary.ts`: the last `permission-mode` record, or else the last `permissionMode` string on any record. No record found means unknown, which with the key unset gives the "may hold" warning. The mode is read per check, on the node only, and never stored. An explicit `accept` is not warned about whatever the mode.

  Outcomes: `refuse` → unavailable `inbound-refused` (fail closed, as for every refusal-type gate). `hold` → available, `inbound: 'hold'`. Unset with bypass or unknown mode → available, `inbound: 'may-hold'`. Anything else → no hint. The warnings never block a send: the owner may want to send and release the message at the terminal.

  The `uds:` prefix is never expected in the JSON (bare path); a value starting with `uds:` fails step 13. Native Windows sessions never reach step 2 (`unsupported-platform`), and the token is never involved, so the spec's `token-required` reason maps to `unsupported-platform` on Windows; it stays in the enum for a platform that a future spike shows requires the token.
- _(Updated 2026-11-17 in 003-b: (i) the `pidDomain` check runs before the liveness test, because a PID from another namespace says nothing here; (ii) a timeout before the connect event wrote nothing, so it is `failed/unreachable`, and only a timeout after connect is `uncertain`; (iii) when several status entries share a session ID, entries whose PID is dead or whose `procStart` differs are ignored, but only when judged in the node's own namespace; one survivor is used, and two live entries or any entry that cannot be judged stay `liveness-unknown`.)_
- **Send errors**: `ENOENT` and `ECONNREFUSED` → `failed/session-ended` if the PID is dead or its `procStart` no longer matches (checked again after the error), else `failed/unreachable`; `ENOTSOCK`, `EACCES` → `failed/unreachable`; `EPIPE`, `ECONNRESET` → `uncertain` if any bytes were written, else as `ENOENT`; timeout → `uncertain`. A failure never retries.
- **Size**: the text limit is 002's (`C9VIEW_CONTROL_TEXT_MAX_CHARS`, 20,000 characters, 400 above it) inside 002's 48 KiB body limit (413). The built frame is also capped at 128 KiB (`FRAME_MAX_BYTES`); 20,000 characters JSON-escaped at worst 6 bytes each plus the wrapper stay under it, so the cap is a defensive 413. Both are far under the receiver's ~1 MB limit (spike Q6) and match the spec's "same size limit as a 002 reply".
- **macOS**: not verified (socket folder, `procStart` format, token behaviour). Recommended: Linux only in this feature, macOS after a re-spike adds its folder and `procStart` rule (decision for the maintainer; FR-018 amendment proposed).
- **Rationale**: FR-003 needs the address tied to the live process and user before every delivery. Node's `net` cannot read the listener's peer credentials, so ownership is shown by: the JSON's PID is alive in the same PID namespace and started at `procStart` (rules out PID reuse), the socket's name is that PID, and the socket and its folder belong to the node's uid with no group or other access (only the same user could have created or swapped it, and the same user is the owner).
- **Alternatives**: `/proc/<pid>/fd` inode matching (rejected: Linux-only detail for little gain over the uid and mode checks); trusting the path as written (rejected: FR-003).

## R8. `ReplyBody.fork` (open question)

- **Users today** (through 002 Phase 8, main dc53729): `packages/api/src/control.ts` (`ReplyBody.fork`); `packages/node/src/control/routes.ts` (reply schema); `packages/node/src/control/service.ts` (`begin`: skips liveness for forks, new ID, `forkSession`); `packages/node/src/control/sdk.ts` (`forkSession` option); `packages/node/src/control/liveness.ts` (both 409 messages say "fork and reply instead"); `packages/node/src/control/service.test.ts` (T021 fork, T024 fork with terminal holder, T033 bypass fork); `apps/web/src/control/api.ts` (`reply(…, fork)`); `apps/web/src/control/Composer.tsx` ("Fork and reply" on `live-elsewhere` and `liveness-unknown`, fork waiting and navigation); `apps/web/src/control/control.test.tsx` (two T042 tests); `apps/web/src/control/recovery.test.tsx` ("Stop waiting unlocks Fork and reply"). In 002 docs: spec US2 summary and scenarios 3–4, FR-009, FR-021's list, FR-025's "forked", the open-question-6 line; plan, research R1, data-model `ReplyBody`, `contracts/control-api.md`, quickstart step 2, tasks T021, T024, T033, T042, design-notes R9.
- **Decision**: **remove fork completely**, including for `liveness-unknown`. After 003, a terminal-live session gets remote send or a refusal (FR-020), and a `liveness-unknown` session gets only the reason (US4 scenario 5: nothing is offered as if safe); no other caller exists. API change: `ReplyBody` loses `fork`, the node's reply schema is `.strict()` so a `fork` field becomes 400, `sdk.ts` loses `forkSession`, and the 409 texts drop "fork and reply instead". This is a non-additive API change, justified in [plan.md](plan.md#complexity-tracking): the only client is c9view's own web, shipped in the same release, and the hub relays bodies unchanged.
- **Alternatives**: keep `fork` for `liveness-unknown` only (rejected: the spec's out-of-scope list rejects forking as a fallback, and US4 scenario 5 refuses with the reason; a dead API branch would need tests and docs for no UI); keep the field but ignore it (rejected: silent).

## R9. API shape

- **Decision**: two machine-scoped routes on the node under 002's control routes, mounted only when control is on (404 otherwise), relayed by the hub like every other `/api/m/:machineId/*` call, POST guarded by `apps/hub/src/control/guard.ts` (already covers every POST under `/api/`):
  - `GET /projects/:projectId/sessions/:sessionId/remote` → `RemoteAvailability`.
  - `POST /projects/:projectId/sessions/:sessionId/remote` with `RemoteSendBody { text, clientRequestId }` → 202 `CommandReceipt` with `delivery`. Reserved under operation `remote` with 002's receipts (`packages/node/src/control/receipts.ts`): one delivery per command, `payload-mismatch`, `unknown-outcome`, tombstones. Replies to the same session run in call order through the same per-session chain as 002's replies, so two tabs' messages are written in the order the node received them.
  - 002's `POST …/messages` keeps refusing a terminal-held session with 409 `live-elsewhere` (the node never resumes a live session); the web never calls it for such a session because availability says `remote`. Details in [contracts/remote-api.md](contracts/remote-api.md).
- **Rationale**: a separate route keeps 002's reply semantics (resume, run state) apart from delivery semantics (no run, transcript-tracked), and keeps every 002 test valid. Availability per session instead of in `ControlRuns`, because it reads files per session and is only needed on the open session page.
- **Alternatives**: overloading `…/messages` to deliver when the session is live (rejected: one route with two outcomes models and a race between liveness and route choice); availability in `/api/machines` (rejected: per-session data).

## R10. Web composer

- **Decision**: `Composer.tsx` gets a mode from the availability query: `reply` (002, when `reason` is `not-live` or `own-run`), `remote` (available), or `refused` (any other reason). In `remote` mode the button reads "Send to the terminal session", a hint above the text area says "This session is open in a terminal. Your message goes into it as a message from another session"; text starting with `/` shows "Slash commands don't run this way; this is sent as plain text"; the `hold` hint shows when reported. `refused` shows the reason and fix ([contracts/remote-api.md](contracts/remote-api.md#reasons-and-fixes)), keeps the text and disables Send, with no fork or "send when free". When the session's status column is `need_input` (existing live-status signal), the page says "Claude is waiting for a decision. Approve in the terminal."
